# Technical Decisions

Short log of significant technical choices and their rationale.

---

## Phase 0

### Prisma 7.10.0 over 8.x-RC
**Decision:** Pin `prisma@7.10.0` (`prev` dist-tag), not `8.0.0-rc.*` (`latest` dist-tag).
**Why:** Prisma 8 is in release-candidate status. A portfolio codebase seen by interviewers should not depend on an RC. 7.10.0 is the last stable release.

### `@prisma/adapter-pg` driver adapter
**Decision:** Use `PrismaPg({ connectionString })` from `@prisma/adapter-pg` instead of the default Prisma engine.
**Why:** The driver adapter gives explicit control over the `pg.Pool`, is compatible with edge runtimes, and is the direction Prisma is investing in for future versions. Required by Prisma 7's recommended setup for PostgreSQL.

### TypeScript ~6.0.3 (not 7.x)
**Decision:** Pin TypeScript to `~6.0.3`.
**Why:** `typescript-eslint@8.x` only supports TypeScript `<6.1`. TypeScript 7 (when released) will require a matching `typescript-eslint` upgrade.

### `typescript-eslint` single package
**Decision:** Use the unified `typescript-eslint` package, not the old separate `@typescript-eslint/parser` + `@typescript-eslint/eslint-plugin`.
**Why:** The unified package is the current recommended approach as of ESLint 9+ and `typescript-eslint` v8+. Fewer packages, single version to manage.

### ESLint flat config (`eslint.config.mjs`)
**Decision:** Use the ESLint flat config format, not the legacy `.eslintrc.*` format.
**Why:** ESLint 9+ deprecated the legacy config format. Flat config is the default and the only supported format in ESLint 10.

### Tailwind CSS 4.x over 3.x
**Decision:** Use Tailwind CSS 4 with `@tailwindcss/postcss`.
**Why:** Next.js 16 ships with Tailwind 4 support. Tailwind 4 is CSS-first (no `tailwind.config.ts` needed for basic usage), which reduces configuration surface.

### Zod 4.x
**Decision:** Use Zod `^4.6.5`.
**Why:** Zod 4 is the current stable major with improved performance and a cleaner API. No reason to use 3.x in a new project.

### `node:crypto` for encryption (no external library)
**Decision:** Implement AES-256-GCM using Node's built-in `node:crypto` module, no third-party crypto library.
**Why:** Eliminates supply-chain risk in security-critical code. Node's crypto module is well-audited and maintained. The implementation is straightforward for AES-256-GCM.

### Auth.js tables in Phase 0 Prisma schema
**Decision:** Include `Account`, `Session`, and `VerificationToken` tables in the initial migration alongside the app models.
**Why:** Auth.js (NextAuth) needs these tables. Adding them now avoids a schema-breaking migration in Phase 3 when auth is wired up. The `@auth/prisma-adapter` v2 schema is stable.

### BullMQ 6.x
**Decision:** Use BullMQ `^6.3.11`.
**Why:** Current stable major. BullMQ 6 uses `ioredis` 5.x which is the widely-used Redis client in the ecosystem. No breaking changes from BullMQ 5 for our use case.

## Phase 1

### `@node-rs/argon2` for password hashing
**Decision:** Use `@node-rs/argon2` instead of `bcrypt` or `argon2`.
**Why:** Provides pre-built native binaries — no compiler toolchain needed, works on Windows without MSVC. Argon2id is the current OWASP-recommended password hashing algorithm. `@node-rs/argon2@2.x` ships binaries for Node 22 + all major platforms.

### undici + custom DNS lookup for SSRF protection
**Decision:** Use `undici` with a pre-connect DNS validation hook instead of a fetch wrapper or a WAF.
**Why:** Validate every resolved IP against the RFC 1918 / CGNAT / link-local / IPv6 blocklist before connecting. Rewrite the URL to use the validated IP and set `Host` / SNI headers explicitly. This prevents DNS rebinding attacks. Manual redirect following (max 3 hops, re-validate each hop) closes TOCTOU gaps. The approach is defence-in-depth at the library level.

### JWT-only sessions (no database Session rows)
**Decision:** Use `session: { strategy: 'jwt' }` for all providers including GitHub OAuth.
**Why:** The Credentials provider requires JWT sessions (database sessions require per-request DB reads for every RSC). JWT is simpler operationally and sufficient for Phase 1. The `Session` table is retained in the schema for the Auth.js adapter's schema compliance.

### No auto-linking of GitHub OAuth to password accounts
**Decision:** If a GitHub OAuth login's email matches an existing password account, return an error instead of auto-linking.
**Why:** Auto-linking can allow account takeover: an attacker who controls a GitHub account with the target email could hijack a password account. The user is shown a clear error message and instructed to sign in with their password.

### Project slug globally unique, immutable
**Decision:** `slug` is globally unique (enforced by `@@unique` in Prisma), validated as `^[a-z0-9-]{3,48}$`, and not editable after creation.
**Why:** The slug is part of the public MCP endpoint URL (`/mcp/:slug`). Changing it would break all existing connections. Global uniqueness avoids URL collisions across users.

### `removedAt` soft-delete on Tool
**Decision:** Add `removedAt DateTime?` to Tool instead of hard-deleting when an operation disappears from a re-imported spec.
**Why:** Preserves user edits and tool call logs. Users can see which tools were removed and the badge ("Removed from spec") makes the state visible. Re-adding the operation to the spec clears `removedAt`.

### Separate `mcpgateway_test` database for integration tests
**Decision:** Integration tests use `DATABASE_URL_TEST` (defaults to `mcpgateway_test` DB), never `DATABASE_URL`.
**Why:** Prevents test runs from corrupting development data. Vitest global setup runs `prisma migrate deploy` on the test DB before tests run, keeping schema in sync.

---

### pnpm `onlyBuiltDependencies` / `allowBuilds` in `pnpm-workspace.yaml`
**Decision:** Explicitly allowlist `@prisma/engines`, `esbuild`, `msgpackr-extract`, and `prisma` for build scripts.
**Why:** pnpm 12 blocks all build scripts by default for supply-chain security. These four packages are known to need native compilation (Prisma query engine, esbuild binary, msgpackr native module). The `pnpm-workspace.yaml` approach is the pnpm 12-recommended way to approve builds without per-developer prompts.

### Root `.env` loaded per app at runtime; validated with Zod at startup
**Decision:** Library packages (`packages/db`) never load `.env`. Each app loads the root `.env` itself — web in `src/instrumentation-node.ts` via `@next/env`, gateway/worker in `src/env.ts` via `dotenv` — then validates it with a per-app Zod schema through the shared `validateEnv`, which throws one error listing every missing/invalid variable and exits.
**Why:** Next.js only reads `.env` from `apps/web`. Calling `loadEnvConfig` from `next.config.ts` looked right but only mutates the CLI process — verified on Next 16 + Turbopack that the server runtime never saw those values. `register()` in instrumentation is documented to finish before any request is served, and middleware reads the same `process.env`, so one load there covers dev and `next start`. CI previously passed only because it set the variables in the job env; a smoke step now unsets `DATABASE_URL`/`AUTH_SECRET` and checks `/api/health` (public, `SELECT 1`), `/api/auth/providers` and the signed-out redirect.

### Tool edits are detected against a stored spec baseline
**Decision:** `Tool` stores `specName` / `specDescription` (what the spec last produced). A user edit is `name != specName`; re-import overwrites `name`/`description` only while they still equal the baseline, and always advances the baseline. `enabled` and `hiddenParams` are never part of an import write. `mergeTools` returns only the rows that changed, so identical specs report `0 updated` and `N unchanged`.
**Why:** The first design relied on a `userEdited` flag that no code ever stored or passed, and the unit tests fed it in by hand, so they passed while the real app silently reverted every edit. A baseline needs no flag to be kept in sync and survives edits made anywhere. Schemas are compared with an order-insensitive deep equal because Postgres JSONB reorders keys, which previously made every tool look "updated".

### Upstream base URL: always absolute, SSRF-checked on save
**Decision:** `servers[0].url` is resolved by `resolveBaseUrl` (variable defaults substituted; relative URLs resolved against the spec URL when imported by URL, left unset for file uploads). Every save path (create, Settings, import) goes through `assertPublicHttpUrl` (http/https only, no credentials, host must resolve to a public address, same blocklist as `ssrfFetch`). An import never overwrites a base URL that is already set.
**Why:** A relative value like `/api/v3` cannot be called, and a private host saved today becomes an SSRF at call time. Failing at save gives the user the reason immediately.

### Tailwind 4 needs the shadcn tokens registered in `@theme inline`
**Decision:** `globals.css` maps every `--background`, `--primary`, … variable to a `--color-*` token and defines `@custom-variant dark` on the `.dark` class.
**Why:** shadcn assumes Tailwind 3's `tailwind.config`. Under Tailwind 4 without the mapping, `bg-primary`, `bg-background`, `text-destructive` etc. compile to nothing, which made switches, dialogs and buttons look broken everywhere at once.

### `server-only` on the web DB wrapper plus a lint rule
**Decision:** `apps/web/src/lib/db.ts` imports `server-only`; ESLint forbids value imports of `@mcp-gateway/db` elsewhere in the web app (type imports allowed). The guard lives in the web app, not `packages/db`, which the gateway and worker run outside React.
**Why:** A client component pulling Prisma into the browser bundle fails the build instead of surfacing as a runtime error. Verified by importing the wrapper from a client page and watching the build fail.

### One PrismaClient per process, in every environment
**Decision:** The lazy `db` proxy always returns the same client (cached on `globalThis`).
**Why:** In production it built a new client per property access, so an interactive transaction began on one client and ran its queries on another ("Transaction not found") and each call leaked a connection pool. Development cached the client and hid it; only a production-build test found it.

### Tool names are unique per project, enforced by the database
**Decision:** `@@unique([projectId, name])` on `Tool` (all rows, including removed ones). The rename action and editor check it first for a friendly inline error; the index is the final word and a lost race is reported the same way. On import, names are assigned in priority order: names a tool already holds (user-chosen, unchanged, or belonging to a removed tool) are reserved first, then spec-derived names that moved, then new tools. A clashing spec name gets `_2`, `_3`, … (kept within 64 chars) and is listed in the import summary. Writes are ordered (park renamed rows on a placeholder, update, then create) because Postgres checks the index per statement.
**Why:** MCP clients address tools by name, so two tools with one name make one of them unreachable. The user's chosen name must never be taken from them by a later spec. A suffixed tool counts as "edited" afterwards (`name != specName`), which keeps re-imports stable instead of flip-flopping. The migration renames pre-existing duplicates (`_dupN`) so it cannot fail on old data.

### `middleware.ts` renamed to `proxy.ts` (Next.js 16)
**Decision:** Renamed per the installed Next 16 docs; the default export and matcher are unchanged. Re-verified in a browser: signed-out redirect, sign-in, `/api/health` public.
**Why:** `middleware` is deprecated. Note the proxy now runs on the Node.js runtime by default (the old middleware ran on edge), so the "edge-safe" wording in our comments was updated. `auth.config.ts` stays free of Prisma/argon2 so the proxy does not depend on the database layer.

### `ssrfFetch` hardening for the gateway
**Decision:** Added JSON/raw request bodies (POST/PUT/PATCH only), one overall deadline (`timeoutMs`, default 15 s, covering DNS, connect, redirects and the body read), a `followRedirects` switch, and blocks for 224.0.0.0/4, 240.0.0.0/4, 198.18.0.0/15 and 64:ff9b::/96. IPv6 checks now work on parsed groups, so alternative spellings of the same address cannot slip past, and unparseable addresses fail closed. Errors carry a `code` (`BLOCKED`, `TIMEOUT`, `TOO_LARGE`, `REDIRECT`, `INVALID_REQUEST`).
**Why:** The gateway forwards agent-supplied data and upstream credentials. Redirects used to re-send every header to any host, which would leak an upstream API key; now only a small allow-list of headers crosses origins, a body is never forwarded cross-origin, and 301/302/303 turn a POST into a GET like a browser. Oversized responses are abandoned instead of drained to the end, and the HTTPS client is closed only after the body is read. Destroying an undici body emits an `error` event, so a listener is attached first; without it Node treats it as an uncaught exception and the process dies.

### MCP SDK v2 (`@modelcontextprotocol/server` + `node`), stateless serving
**Decision:** The gateway uses the v2 SDK (`@modelcontextprotocol/server` 2.3.1, `@modelcontextprotocol/node` 2.1.1), the low-level `Server` with `setRequestHandler('tools/list' | 'tools/call')`, and `createMcpHandler` with a fresh server per request: no sessions, `legacy: 'stateless'` (the default) so clients on the 2025 handshake are served too. `@modelcontextprotocol/sdk` 1.32.1 is a dev dependency only, used by a test proving older-protocol clients can list and call tools. The stack tables in `SPEC.md` and `CLAUDE.md` were updated.
**Why:** `@modelcontextprotocol/sdk` is now the v1 maintenance line (spec 2025-11-25); v2 is the current stable release and the one MCP Inspector 2.9 is built on. Stateless fits a multi-tenant gateway on free hosts that restart often, scales without sticky sessions, and nothing here needs server-initiated messages. Verified with a spike (`apps/gateway/examples/`): the v2 client (legacy, `auto` and pinned-2026 negotiation), the v1 client and Inspector's CLI all list and call tools against the same server. The low-level server does not validate arguments, so the gateway validates them with the SDK's own Ajv entry (`@modelcontextprotocol/server/validators/ajv`), which means no direct `ajv` dependency.

### One description of a tool's arguments, shared by schema and request
**Decision:** `describeOperation` in `openapi-tools` produces, per operation, each argument's schema *and* where it goes on the wire (path, query, header, cookie, JSON/form body property, or whole body). `extractTools` builds the input schema from it and the gateway builds the HTTP request from the same description via `buildRequestMap` + `buildRequest`; a test asserts the two agree for every operation in the fixtures. The map is derived from the stored spec rather than saved per tool. Arguments that share a name across locations (a path `id` and a body `id`) are no longer merged: path > query > header > cookie > body, and a later clash is renamed with its location (`body_id`, then `_2`, …). `toAgentSchema` (hidden parameters removed) moved from the dashboard component into the package so the dashboard preview and the gateway's `tools/list` cannot differ.
**Why:** The old extractor keyed arguments by name alone, so a clash silently dropped one of them, and nothing recorded which arguments were path, query or body, which the gateway needs. Deriving instead of storing avoids a migration and a second copy that could go stale. Re-importing an existing project rewrites a stored schema that differs (it counts as "updated") while keeping the user's edits. Limits: object-valued query parameters are sent as JSON, cookie parameters go in one `Cookie` header, and multipart/XML bodies are not supported. Path values of `.` or `..` are rejected because they would be resolved as dot-segments and escape the intended path.

### Gateway request path: authenticate first, one stateless handler, errors as tool results
**Decision:** `POST /mcp/:projectSlug` authenticates before the SDK sees the request: `Authorization: Bearer <key>`, SHA-256 hash looked up (Redis, then Postgres), the key's project must match the slug, and every failure (missing, malformed, unknown, revoked, another project's key, unknown slug) returns the same 401 so slugs cannot be enumerated. One SDK handler is built at startup; the authenticated project travels to its per-request server factory through `authInfo`, so nothing is shared between tenants. `GET`/`DELETE` return 405. A tool call validates arguments with the SDK's Ajv entry, merges hidden values last so they always win, builds the request, adds the credential, and calls `ssrfFetch` with no redirects, a 15 s deadline and a 1 MB cap. Every failure (validation, upstream 4xx/5xx, timeout, oversize, redirect, blocked host, unreachable) is an `isError` result with fixed wording, not a protocol error or a crash; an unknown, disabled or removed tool is the same protocol error (`-32602`).
**Why:** The SDK handler deliberately does no authentication, so it must be placed behind our check. Returning failures as results lets the model read and correct them, and a thrown error would hide them behind a generic one. Messages never contain the request URL or headers, and all outgoing text is scrubbed of the credential in its raw, URL-encoded and base64 forms, because upstream error pages often echo the request (verified, including on successful responses).

### Redis is a cache, not a dependency; invalidation is explicit
**Decision:** Per-project config (`mcp:cfg:<slug>`: base URL, encrypted credential, enabled tools with their request maps) and API key lookups (`mcp:key:<hash>`, with a 10 s negative entry) live in Redis. Every Redis failure is a cache miss plus a warning, so an outage makes the gateway slower, not down. Entries expire on their own (config 5 min, keys 30 s), and the dashboard deletes them on every edit through helpers in `packages/shared`. `lastUsedAt` is written at most once per key per 5 minutes per instance, in memory and off the request path.
**Why:** The spec asks for a Redis cache with a Postgres fallback. The TTLs bound staleness if an invalidation is lost (a revoked key can work for at most 30 s then), and the config cache holds the credential still encrypted so Redis never sees plaintext. A shared-Redis throttle for `lastUsedAt` would make a cache outage cost a write per call; the dashboard only shows minutes.

### `DATABASE_POOL_MAX`: an explicit cap on Postgres connections
**Decision:** `packages/db` reads an optional `DATABASE_POOL_MAX` (default: the pg driver's 10). Test setups set it to 3.
**Why:** A full `pnpm test` runs a dozen vitest workers, each with its own client, against a Postgres limited to 100 connections; one run hit "Unable to start a transaction in the given time". The same limit matters in production: free-tier hosted databases allow few connections, and each gateway or web process opens its own pool.

### Dashboard: keys shown once, credentials write-only, cache invalidation fails open
**Decision:** An API key is generated server-side and returned in one response; only its SHA-256 hash and a short prefix are stored, and the reveal dialog cannot be dismissed by Escape or a stray click. Upstream credentials are write-only: the browser receives only `{ type, names, hasValue }`, shows `••••••••` and a Replace button, and an empty value means "keep the stored secret", but only when the kind is unchanged (a secret is never carried over to a different scheme). Header names are validated as RFC 9110 tokens and gateway-controlled headers (Host, Content-Length, …) are refused; values containing control characters are refused to stop header injection. Every action that changes what the gateway serves clears the right Redis key through `CacheInvalidator`, which logs a warning and carries on if Redis is down, then stops trying for 30 s. The rate limit is stored and shown on each key (enforced since Phase 3, see below).
**Why:** Showing a secret once is the only way to keep it unrecoverable. A credential that can be read back is a credential that can leak through the browser, logs or screenshots. Redis only caches what Postgres already holds, so a failed invalidation must not fail an edit that has already been saved; the cache TTLs (5 min config, 30 s keys) bound the damage, and the short timeouts mean an outage costs one brief delay rather than one per click.

### The gateway ships as a standalone image built with `pnpm deploy`
**Decision:** `apps/gateway/Dockerfile` (build context: the repo root) installs only what the gateway needs (`--filter @mcp-gateway/gateway...`), compiles the workspace packages in dependency order, and uses `pnpm deploy --prod` to extract a self-contained folder into a clean `node:22-slim` runtime stage. It runs as the non-root `node` user with node as PID 1 (the gateway drains on SIGTERM), has a `/health` healthcheck on whatever port `PORT` names, contains no source, tests or `.env`, and is configured only by environment variables. It does not run migrations. CI builds the image and checks all of that, in a job that runs in parallel with the main one.
**Why:** The gateway must run anywhere (Render, Koyeb, a VM) from environment variables alone, with no reliance on a repo checkout. `pnpm deploy` is the supported way to produce that folder from a workspace; the multi-stage layout keeps compilers and dev dependencies out of the runtime. Known cost: the image is about 820 MB uncompressed, mostly Prisma's client and the tooling it pulls in as peers, and a cold build takes minutes because pnpm 12 verifies every lockfile entry against the registry's release-age policy (a supply-chain protection we leave on).

### Gateway dev runs under `node --watch`, and startup is guarded so it can never fail silently
**Decision:** The gateway `dev` script is `node --watch --import tsx src/index.ts` instead of `tsx watch`. `src/index.ts` is now a tiny entry that loads `main.ts` through a dynamic import inside `runStartup` (`src/startup.ts`): any import or startup error is logged as `[gateway] Gateway failed to start: ...` and the process exits 1, and a watchdog (`GATEWAY_STARTUP_TIMEOUT_SECONDS`, default 60) logs a clear message and exits 1 if the server is not listening in time.
**Why:** Under Turbo on Windows, `tsx watch` never finished loading the gateway's large import graph (tested to 240 s) and printed nothing, so `pnpm dev` showed no "Server listening" line and no error. `tsx src/index.ts` and `node --watch --import tsx` start in about 8 s in the same setup and still restart on edits. ES module imports are evaluated before any code in the importing file, so the guard had to sit in a file with no heavy imports. Redis and Postgres are not awaited before `listen`, so they were not the cause.

### Gateway dev restarts on content changes only, via a small runner (supersedes `node --watch`)
**Decision:** `pnpm dev` runs `apps/gateway/scripts/dev.mjs`, which starts `node --import tsx src/index.ts` and restarts it only when the content hash of a watched file changes. Watched: `apps/gateway/src`, the `dist` folders of `shared`, `crypto`, `db` and `openapi-tools`, and the root `.env`. Events whose content is unchanged are ignored; real edits are debounced to one restart.
**Why:** On Windows with NTFS last-access updates enabled (the default), the first read of a file in an hour is reported as a "change" event. `node --watch` restarts on any event, so the web app compiling a page, the worker starting, or the gateway reading its own files restarted the gateway in a loop (`--watch-path` was worse: its watchers exist before the gateway's own startup reads). Watching content instead of events is immune to this. Cost: about 80 lines of script and no new dependency; a package's `src` edit still needs a rebuild of its `dist`, as before.

### Tool annotations come from the HTTP method; 401s say "API key", not OAuth
**Decision:** `tools/list` returns annotations derived from the upstream method (`annotationsForMethod`): GET/HEAD are read-only; DELETE is destructive and idempotent; PUT is idempotent; POST/PATCH change state and are not idempotent; every tool is open-world. The 401 body reads "API key missing, invalid or revoked…" (one message for all causes, so project slugs still cannot be probed), and unknown routes, including OAuth discovery URLs such as `/.well-known/oauth-protected-resource`, get a JSON 404 straight away. No OAuth is implemented.
**Why:** Without annotations, clients assume the worst, so the Inspector showed a GET as "Destructive". After a 401 the Inspector tried OAuth discovery and reported a confusing "OAuth Authentication Failed"; an explicit, fast 404 and a message that names the API key point people at the real problem. Annotations are hints for UIs only, never a security control.

## Phase 3

### Rate limiting: exact sliding-window log in one Lua script, `tools/call` only
**Decision:** Each API key's limit (`ApiKey.rateLimitPerMin`, tool calls per rolling 60 s) is enforced with a Redis sorted set per key (`mcp:rl:<apiKeyId>`): one member per accepted call, scored by its time. A single Lua script trims old members, counts, and either rejects (returning the exact seconds until enough of the oldest calls leave the window) or adds the call and sets the expiry, so concurrent requests, even from several gateway instances, cannot pass the check together. Only `tools/call` messages count, a JSON-RPC batch counts once per `tools/call` in it, and rejected calls are not recorded. The check runs after authentication and before the SDK sees the request, so a rejected call never reaches the upstream and unauthenticated traffic cannot create counters. The answer is HTTP 429 (kept as a status, not a 200 with `isError`) with `Retry-After`, `RateLimit-Limit/Remaining/Reset` and a JSON-RPC error body (code -32029) whose message names the limit and the wait.
**Why:** A fixed window lets a caller double the limit across a boundary, and an approximate counter gives only a guessed `Retry-After`; the exact log is O(limit) memory per active key, bounded by the 10,000 cap, and one command per call. The handshake (`initialize`, `tools/list`) repeats on every stateless connection and never reaches the upstream, so counting it would spend quota on overhead. Gap accepted: `tools/list` is not limited in this phase (it is served from cache). The script takes the time from the gateway instead of Redis `TIME` so it contains no non-deterministic command, which some hosted Redis plans refuse; a few milliseconds of skew between instances do not matter against 60 s. MCP clients (SDK v1 and v2) print the response body, not the status line, so the wait time has to be in the message text; the status and headers are for HTTP-aware callers and browsers (`retry-after` and `ratelimit-*` are exposed through CORS). A 429 makes the client throw, so the host application sees it rather than the model; that was chosen over `200 + isError` on purpose.

### Rate limiting fails open when Redis is down (no local fallback)
**Decision:** If the Lua call fails, the call is allowed. A circuit breaker (5 s) then skips Redis entirely so a hung Redis does not add its command timeout to every call, and one warning is logged per breaker window. There is no in-memory fallback limiter.
**Why:** The gateway already treats Redis as a cache, not a dependency (see "Redis is a cache"), so an outage should slow it down, not stop every customer's agents. **Trade-off:** while Redis is unreachable nothing is limited, so a key can send as many calls as the gateway and the upstream can take, and the publisher's API is protected only by its own limits. A per-instance in-memory limiter would cap that at N times the number of instances, but it is a second implementation of the algorithm to keep consistent and test, which this phase chose not to carry. The warning log and the breaker make an outage visible and bounded in cost.


### The rate limiter's clock is the gateway's, not Redis `TIME` (changed during Phase 3)
**Decision:** The plan had the Lua script read Redis `TIME`. The script instead takes `now` as an argument from the gateway (`Date.now()`), and uses it for trimming, scoring, expiry maths and `Retry-After`.
**Why:** `TIME` is a non-deterministic command inside a script, and some hosted Redis plans (the free tier this is meant to deploy on is one candidate) refuse or restrict that; finding out at deploy time is worse than not depending on it. The cost is clock skew between gateway instances, which is a few milliseconds with NTP and irrelevant against a 60 s window. Taking the time as an argument also lets tests move the clock (`AppConfig.rateLimitNow`) instead of sleeping.

### Call logs: bounded buffer, batched writes, the event id is the primary key
**Decision:** The gateway never writes a log row on the request path. `CallLogger` builds a `LogEvent` (with arguments already masked and bounded) and calls `LogSink.enqueue`, which is synchronous and cannot throw. A `BufferedLogSink` holds up to `LOG_BUFFER_MAX` events (a full buffer drops the new event and counts it, warning at most once per 30 s) and a timer writes them in batches. A failed or timed-out write puts the batch back at the front and retries with backoff. `close()` runs in the app's `onClose` hook, before Redis and Postgres are disconnected, and keeps trying until `LOG_SHUTDOWN_FLUSH_MS`. `ToolCallLog.id` is the gateway-generated event id (no database default), so inserting a batch twice stores it once (`createMany` with `skipDuplicates`).
**Why:** Logging must never slow or fail a tool call, and a database or Redis outage must not take calls down. Dropping the newest keeps the start of an incident and costs O(1). The per-write timeout exists because BullMQ's `Queue.add` does not reject while Redis is down: it waits for the connection, which would have stuck the single writer forever (found by a test). A write that was only slow may still land later, and the event ids make that harmless. Accepted loss: a SIGKILL or crash loses up to one flush interval of events (measured: 5 calls made, 0 rows survived a `docker kill`; a `docker stop` wrote all of them).

### Queue mode sends one job per batch; direct mode is the same sink with a different writer
**Decision:** In `queue` mode each batch is one BullMQ job and the worker writes it with one `createMany` (open-source BullMQ has no batch consumer, so the batching happens on the producer side). `LOG_SINK=direct` swaps only the writer: the gateway calls the same `writeLogBatch` the worker uses, BullMQ is never imported, and nothing polls Redis for logs. `queue` stays the default; the deploy guide sets `direct`.
**Why:** The free Upstash plan cannot afford BullMQ's polling, and the deployed gateway should not need a second process. Sharing the buffer, retry and shutdown code between modes means one implementation to test.

### What is stored, and what is not
**Decision:** Never stored: response bodies (only the size), the request URL, query strings, redirect `Location` values, upstream credentials, hidden-parameter values, API keys or anything derived from them. The error message is the first line of the gateway's own fixed wording, passed through `sanitizeErrorMessage` (URLs and query strings removed, 300 characters). Arguments are what the agent sent, masked by key name (authorization, password, token, secret, api key, cookie, credential, private key), by `format: password` / `writeOnly` in the tool's schema, and by value shape (API keys, Bearer/Basic values, JWTs), then bounded in depth, items, keys, string length and total size. The masker stops walking at those limits instead of cutting afterwards, so a 1 MB argument costs about as much as a small one. Masking happens in the gateway, before the event is queued, so a secret never reaches Redis. The `ToolCallLog.output` column was dropped.
**Why:** A log table full of upstream response bodies is a second copy of the publisher's customers' data. Query-parameter credentials are appended to the URL we call, and upstream errors and redirects echo URLs, so every route a URL could take into a stored message is closed and tested for each error class, in the stored row and in the raw queue payload.

### Auth failures and rate-limit rejections are sampled and filed under the URL's project
**Decision:** An auth failure stores the slug from the URL, a reason (`AUTH_MISSING`, `AUTH_INVALID`, `AUTH_WRONG_PROJECT`) and nothing about the key; the writer resolves the slug to a project in one query per batch and drops unknown slugs. A key used on another project's URL is logged under the URL's project with no key id (the key is another tenant's). These events, and rate-limit rejections, are sampled to one per slug-or-key and reason per 10 s per instance, with a global cap, in a bounded map.
**Why:** The sender is unauthenticated (or hammering) and could otherwise write unlimited rows. Resolving slugs off the request path costs nothing there. Consequence: counts of these classes are "at least". The writer also keeps a tool or key id only if it belongs to the event's own project.

### Retention runs wherever the logs are written
**Decision:** `purgeOldLogs` deletes rows older than `LOG_RETENTION_DAYS` (default 30) in batches of 5000 and is idempotent. Both modes run it about a minute after boot (with jitter) and then every 6 h. Queue mode: the worker uses an idempotent BullMQ job scheduler (`upsertJobScheduler`, so restarts keep one schedule) with `startDate` set a minute ahead. Direct mode: the gateway uses timers.
**Why:** Direct mode has no worker, so the gateway has to do it. A host that sleeps when idle writes no logs while asleep, so a run at wake-up is enough; the worker runs at boot too. BullMQ queues a scheduler's first run immediately on every upsert (measured), which would run the delete on every start of a crash-looping worker, so the first run is delayed with `startDate`. Concurrent runs from several instances are harmless. It needs an index on `created_at` alone, which the migration adds.

### `UsageRollup` removed; Phase 4 reads the raw logs
**Decision:** The `usage_rollups` table was dropped (nothing referenced it). Phase 4's charts query `tool_call_logs` with `(project_id, created_at)` and `(project_id, tool_name, created_at)`. `tool_id` and `api_key_id` are indexed too, because Postgres does not index foreign keys and deleting a project cascades to both.
**Why:** Rollups would be written by the worker, which does not exist in the worker-less deploy mode, so a dashboard built on them would be empty there. With 30-day retention the raw table stays small enough to aggregate on demand.

### Two shared-package details that mattered
**Decision:** `@mcp-gateway/db` imports `@mcp-gateway/shared/log-event` (a subpath export), not the whole package. Test Redis clients have no `commandTimeout`.
**Why:** Importing all of `shared` pulled undici and the SSRF code into every consumer of the db client, which showed up as a slower cold import in the web tests. A 500 ms command timeout in the test harness made healthy Redis calls fail on a loaded machine, which silently turned cache hits into misses and made the (deliberately fail-open) limiter allow calls.

## Phase 4

### Analytics: resolve the owned project id first, then query logs by that id
**Decision:** Every analytics function takes `{ userId, slug }` and starts with `ownedProjectId` (`WHERE slug = $1 AND user_id = $2`); every log query then filters on `project_id = $id`. The SQL builders are private, so no caller can pass a project id of its own. A project the user does not own gives `null` from every function, the same as an unknown slug.
**Why:** The first version joined `projects` inside each statement. The planner cannot know the project at plan time, so for a small tenant on a table shared with large ones it chose a sequential scan of the whole table (7 d summary) and a backward walk of the global `created_at` index (recent calls); measured on 408 rows among 100k, 38 ms and 8 ms versus 0.8 ms and 0.2 ms once the id is a bound parameter. The cost of the look-up is one indexed read.

### Analytics: instants leave SQL as UTC wall-clock, bounds are converted explicitly
**Decision:** `tool_call_logs.created_at` is `timestamp(3) WITHOUT time zone` holding UTC. Window bounds are computed as `timestamptz` and converted with `AT TIME ZONE 'UTC'` before they are compared with the column (which also keeps the `(project_id, created_at)` index usable). Every instant returned (`first_start`, `ts`, bucket starts) is converted the same way, so it comes back as a plain timestamp.
**Why:** Two separate traps, both invisible on a UTC database. Comparing a naive column with a `timestamptz` makes Postgres read the column in the *session* time zone, which shifts both bounds by the session offset. And the Prisma pg adapter reads a `timestamptz` by rewriting its printed offset to `+00:00` without converting, so a non-UTC session returns wrong instants. The Node process time zone does not matter: the adapter writes a `Date` with `getUTC*`, and raw SQL passes `now` as an ISO string with `Z`. The analytics tests therefore run on a Los Angeles database session, with boundary rows 1 ms either side of the window; removing either conversion makes the suite fail, while on a UTC session the same removals pass. Verified on Node with `TZ` set to UTC, `America/New_York` and IST (on Windows, Node only honours `TZ=UTC` and POSIX names such as `EST5EDT`).

### Analytics: what counts, and which window
**Decision:** A "call" is a `TOOL_CALL` row that is not `RATE_LIMITED`. Rate-limited rows (sampled, latency 0) and auth failures (sampled) appear only as "at least" counts. p50/p95 use `percentile_cont` over all calls, so they are the gateway's end-to-end latency, including fast validation failures. The window is the buckets themselves: 24 hourly buckets, or 7 / 30 local days including today, aligned to the viewer's time zone; cards, chart, top tools and recent calls share its start, so "24 h" covers 23 to 24 hours and "7 d" covers 6 days plus today.
**Why:** Sampled zero-latency rows would drag p50 towards 0 and make totals depend on the sampling. Aligned buckets are what a chart can draw without a partial first bar, and one shared start means every number on the page adds up.

### Web tests: a longer hook timeout only where the hook does a cold import
**Decision:** The `beforeAll` in `redis-unavailable.test.ts` has an explicit 60 s timeout. `apps/web/vitest.config.ts` keeps Vitest's defaults.
**Why:** That file failed once in a full run with "Hook timed out in 10000ms". Reproduced on demand by loading the CPU (12 busy loops on 4 cores): its `beforeAll` cold-imports the whole action graph, 2.5 s on an idle machine and 8.2 s when starved, then writes to the database. The same hook passed in 10.3 s under the same load with a longer limit. Nothing was shared between files (the Redis URL is stubbed per file, the rows are uniquely tagged); the default was shorter than the real work. Raising it for that one hook leaves every other test's timeout meaningful.

### Web tests under load: pay the cold start once, give real work its own limit, assert behaviour not a stopwatch
**Decision:** (supersedes the entry above where it says Vitest's hook default is kept.) `apps/web/src/test/setup.ts` builds the database client and runs one query before each test file, then throws that client away. `hookTimeout` in `apps/web/vitest.config.ts` is 60 s; `testTimeout` stays at the 5 s default. Tests whose own work takes 0.15 s or more idle (seeding 200 rows, a 41-row pagination walk, two or three spec imports, argon2, a transaction round trip) have an explicit `timeout` with a comment giving the idle and starved times. `db-client.test.ts` warms its own fresh-client path in a `beforeAll`. The `redis-unavailable` check counts attempts on the dead Redis instead of timing five edits. `cache-invalidation.test.ts` gives the dashboard's Redis client no command timeout, as the gateway test client already has none.
**Why:** The full suite flaked on a starved CPU, and "load" was not an answer, so it was reproduced and measured (12 busy loops on 4 cores, per-test durations from the JSON reporter, idle against starved). Where the time went: the first query of a worker took 3.7 s starved against 0.2 s idle (it builds the client and loads the query compiler), and it landed in whichever test or hook came first; the first `PrismaClient` built in `db-client.test.ts` took over 5 s; seeding 200 rows took 0.46 s idle and 5.1 s starved. Postgres was not the bottleneck: 21 samples of `pg_stat_activity` showed no lock waits, only `Client idle` and `IO`. Four different files then hit the 10 s hook default, so one global hook limit replaced a 60 s on 16 files. Two of my own fixes needed fixing: warming the singleton in `setup.ts` left a UTC connection in the pool, which made the analytics time-zone tests run on the wrong session (the analytics fixtures set `PGOPTIONS` after setup), hence the throwaway client; and a wall-clock assertion (`< 1500 ms`) measured the machine, not the code. A third cause surfaced only after those: the dashboard's own Redis client times out after 1 s, so on a starved machine one `DEL` failed, the invalidator paused for 30 s and `cache-invalidation.test.ts` saw seven keys that were never deleted. Result, with the web suite alone under the load: 1 of 3 runs green after the warm-up and hook limit, 2 of 3 after the per-test limits, 3 of 3 after the Redis-client change; then `pnpm test` (all packages) 3 of 3 under the same load, where an earlier attempt part-way through had passed 0 of 3. What this does not do: a 5 s limit cannot survive unlimited starvation. A test that takes 50 ms idle can still reach several seconds with 12 spinners on 4 cores (`createApiKey` reached 3.8 s), and none reached 5 s in the six final loaded runs; if one does, check its idle time first and give it a limit only if its own work is heavy.

### Analytics tab: zone from a cookie, range in the URL, actions return results
**Decision:** The page reads the `viewer_tz` cookie. With no cookie it renders a skeleton plus a small client component that reports the browser's zone to a server action (which sets the cookie) and refreshes; the cookie holds whatever the browser sent, and the page resolves it against Postgres' zones, so a junk value shows "Showing UTC" instead of repeating the round trip. The range is `?range=` parsed with `z.enum(...).catch(default)`. "Load more" and the detail dialog are server actions that call `auth()`, validate with Zod and return `{ ok, error: 'unauthenticated' | 'not_found' | 'invalid' }`; the first page's `windowEnd` is sent back as `now`, so paging never moves the window. The detail action returns only the masked input, error message and response size. The chart is hand-written SVG with an HTML tooltip and a visually hidden table (no chart library).
**Why:** The server has to know the zone to bucket days, and a cookie is the only way to have it on the first server render after the first visit. Plain URL params keep ranges linkable. Result values (not thrown errors) let the client tell a stale page from a bad request, and let tests assert each case. The spec asks for a lightweight chart library; two stacked series do not need one, and the ask-before-adding-a-dependency rule favours not adding one.

### Analytics seed: inputs come from each tool's schema and go through the real masker
**Decision:** `seed:analytics` builds each call's arguments from the tool's stored `inputSchema` (names, types, enums, bounds; hidden params skipped) and passes them through `maskArguments`, imported from the new `@mcp-gateway/shared/mask` subpath. Secrets get a realistic plain value in the generator; the masker is what hides them.
**Why:** A hand-written `[MASKED]` could drift from what the gateway really stores, and a generic `{status}` on every tool made the detail dialog look fake. A subpath keeps `undici` out of the db package, as with `log-event`.

### Analytics seed: a password is never sent without its account name
**Decision:** When a seeded call includes a password-like string, the generator also includes the first of these string properties the schema has (exact name, case-insensitive): `username` / `user_name`, then `login`, then `email`. An `email` value is the sibling username at `example.com`; a phone is a `+1-555-01xx` fictional number. VALIDATION rows use the gateway's own wording and describe their own input (a missing required property, else a plain property of the wrong type); a gateway test compares them with the real Ajv validator.
**Why:** In the real Petstore spec `loginUser` has both parameters optional, so one call in four sent a password alone, which no agent would do. A name pattern such as `/user/` would also match `userStatus` and `userId`, and in `createUser`'s property order would pair the password with `email`. The hardcoded `id must be integer` on an empty input was wrong for almost every tool, and a copy of the message in the seed would drift from the gateway unless a test ties them together.

### One test database per package
**Decision:** `web`, `gateway` and `worker` each run their tests on their own database (`mcpgateway_test_web`, `_gateway`, `_worker`). `DATABASE_URL_TEST` is the base name; `prepareTestDatabase(suite)` (`@mcp-gateway/db/test-database`, called from each `global-setup.ts`) derives the name and runs `prisma migrate deploy`, which also creates a missing database. The CI steps that created and migrated one shared test database were removed. This supersedes "Separate `mcpgateway_test` database" above.
**Why:** CI run #42 failed with the 30 d call count one short (the 20-day-old fixture row missing). `turbo` runs the package suites at the same time, and `purgeOldLogs` deletes by `created_at` across the whole table. Reproduced on demand: a loop calling `purgeOldLogs` with the clock set 10 days ahead (what `log-retention.test.ts` does once) while the web analytics tests ran gave the same assertion failure in the first run; with the loop off it passes. It was worse than the shifted clocks: gateway `log-direct.test.ts` runs a sink with `retentionDays: 7`, and the worker retention test purges every 200 ms, both on the real clock, and the web fixtures sit at a fixed date, so today's date alone decides how many of them a real-clock purge removes (from 22 Oct 2026 the 30-day purges would reach the 20-day-old rows on their own). Separate databases remove the whole class. Serialising turbo would also have hidden it, but would make CI slower and leave the fixtures one purge away from deletion in any single-package run. Redis needed no change: queue names in tests are random and the other keys are per slug or key hash. The gateway's own test files shared one database at this point, so its retention tests could in principle delete rows another gateway file aged on purpose (fixed in the entry "Gateway retention tests get their own database" below); the `now + 31 days` test, which would have deleted every row, now uses a cutoff that only reaches its own row.

## Phase 5

### Hidden parameter values are not secrets, so responses are not redacted for them
**Decision:** The only thing redacted from what comes back from the upstream, in the MCP tool result and in the Playground's response preview, is the project credential (plain and in its encoded forms). A hidden parameter's fixed value is not added to the redaction list. The Playground's request preview still shows `HIDDEN` in its place, built structurally (a second request build with the placeholder), not by replacing text. The Parameters tab says the values are stored as plain text and that secrets belong in the project credential.
**Why:** A hidden value is a fixed setting, usually an ordinary word, and it is stored unencrypted and shown to the owner in the editor, so there is nothing to protect. Redacting it as text corrupts data: with `status` hidden as "available", every pet in the Playground's response read `"status": "[REDACTED]"`. The same thing had already happened to `true`, `false`, `null` and numbers, which were fixed one type at a time; this removes the whole class instead of the next word. A secret that is hidden from agents but should not be readable belongs in the encrypted credential, which stays redacted. Checked against the code: the MCP path never put hidden values on its list (its list was the credential only), so agents were not affected, and only the Playground's response and request text were; a header whose value happened to equal the hidden word was also masked in the request preview. The cost is small and accepted: if an upstream echoes a hidden value back, the response shows it as the upstream sent it.

### The Playground runs through a signed internal gateway route, not through `/mcp` with a key
**Decision:** The Playground's server action (`apps/web/src/actions/playground.ts`) signs a request with `PLAYGROUND_SECRET` and posts it to `POST /internal/playground/:slug/run` on the gateway. The route runs `callUpstream(..., { preview: true })`, the function behind `/mcp`, and returns only the masked request and response. It exists only when the secret is set (`apps/gateway/src/app.ts:73`), allows 30 calls a minute per project (`routes/playground.ts:21`, `PLAYGROUND_RATE_PER_MIN`), requires `confirmed: true` for any tool that is not a GET (`:106`, and again in the dashboard), and writes no `tool_call_logs` row. Rejected: calling the upstream from the web app, and sending the call to `/mcp` with an API key.
**Why:** The dashboard has no API key to send: keys are hashed and shown once (`packages/crypto/src/apikey.ts:7,21`). Minting a hidden key for it would put a credential in the database whose only job is to be used by the dashboard. `/mcp` also counts each call against a key's limit (`routes/mcp.ts:96`) and logs it (`mcp/server.ts:64`), so Playground runs would show in Analytics as agent traffic, and it returns result text without the request, which is what the Playground exists to show. Calling the upstream from the web app would have meant moving the call path (validation, SSRF guard, timeout, size cap, redaction) into a package both apps use and giving the web host the job of decrypting the upstream credential; with the route there is one copy, and the credential is only ever decrypted in the gateway. The cost is a second shared secret, one more hop (the dashboard waits the tool timeout plus 5 s, `packages/shared/src/timeouts.ts`), and a "gateway not reachable" state. The risk accepted: whoever holds the secret can run any project's enabled tools with its stored credential (not read the credential). It is bounded by the 60 s signature window, the single-use nonce, the per-project limit, the confirmation for tools that change data, and the route not existing unless the secret is set. A browser cannot make the call, because it cannot compute the signature. The Playground's 30 per minute limit fails open if Redis is down, like the per-key limiter (`ratelimit/limiter.ts:89`): it protects the customer's API, not the gateway. Running without logs means no `source` column or migration was needed now; adding one, so Playground runs could be shown separately in Analytics, is a later step.

### The Playground's replay check fails closed
**Decision:** The gateway remembers each request's nonce with `SET mcp:pg:nonce:<nonce> NX` and a 120 s expiry (`apps/gateway/src/routes/playground.ts:25,83`). A nonce it has seen is `401 replayed`. If Redis cannot answer, the request is refused with `503 playground_unavailable` and nothing runs (`:85-87`). Tested with the gateway pointed at a Redis that is not there (`apps/gateway/src/test/playground.test.ts`, "Redis unavailable").
**Why:** Everything else about Redis in this project fails open, on purpose: a cache miss is only slower (see "Redis is a cache, not a dependency"), and a limiter that cannot count lets calls through rather than taking every customer down. This check is different in kind. It is a security control, not a convenience. Failing open would turn "Redis is down" into "any signed request that was captured can be sent again", and a request for a tool that changes data, with `confirmed: true`, re-sends a POST or DELETE with the stored credential. The signature window is 60 s each way (`packages/shared/src/playground-signature.ts:14,58`), so a request can be valid for up to 120 s; the nonce is kept for twice the window (`routes/playground.ts:25`) so it outlives every timestamp that could still be accepted. The cost is that the Playground is unavailable while Redis is down; `/mcp`, which fails open, is not affected. The dashboard shows "The gateway is not available right now" for the 503.

### Gateway retention tests get their own database
**Decision:** The two gateway test files that run retention (`log-retention.test.ts`, `log-direct.test.ts`) use a second database, `mcpgateway_test_gatewayretention`, created and migrated by the gateway's `global-setup.ts` like the others. Each calls `useRetentionDatabase()` before its first query; every other gateway file keeps `mcpgateway_test_gateway`. A test scans the test directory and fails if a file that runs `purgeOldLogs` or the retention timer does not switch, or if another file does. Not the Vitest `projects` split. (The name has no underscore after `gateway` because the suite-name rule allows only lower-case letters and digits.)
**Why:** `purgeOldLogs` deletes every old row in its table, whoever wrote it, and the sink's retention timer calls it every 20 to 100 ms in these tests. The per-package databases (above) stopped one package's purge reaching another's rows, but left this case inside the gateway suite. Nothing was failing: no other gateway file writes rows older than a few days, so it was a latent hazard, and the entry above recorded it as "not fixed by this". The isolation is proved rather than assumed: a test writes a 100-day-old row to the main gateway database, purges on the retention database and checks the row survives; and with the switch removed the isolation tests and the scan fail. The cost is one more `migrate deploy` of a few seconds in setup. A per-file switch was preferred to a second Vitest project because the two files still share the harness, the setup and the Redis settings.

### The analytics seed helpers live behind `@mcp-gateway/db/seed`
**Decision:** `seedAnalyticsLogs`, `buildSeedEvents`, `assertSeedAllowed`, `sampleInvalidInput` and the rest of the seed code are exported from the subpath `@mcp-gateway/db/seed` (`packages/db/src/seed.ts`), not from the main entry. Their importers are the two seed test files and the seed script (which imports by relative path). A test in the gateway suite walks the static import graph of the built main entry and fails if a seed module is on it, checks the main entry exports none of the helpers, and checks that nothing the gateway, worker or dashboard ships imports the subpath.
**Why:** The main entry is what the gateway imports, and it re-exported the seed code, so every gateway start loaded `analytics-seed.js` and `seed-input.js` (measured with a Node resolve hook: 161 modules loaded by the gateway app before, 159 after, the two seed modules the difference). Dead code in a request-serving process is a small cost but a real one, and it kept a development tool in the surface the production path depends on. The subpath mirrors `./test-database`. What this does not do: the two files are still compiled into `dist/` and into the Docker image, because the package is deployed whole (`apps/gateway/Dockerfile`); they are no longer loaded. Dropping them from the image belongs with the "slim image" work in 5b.

### The dashboard at phone width: a drawer below `md`, and every grid sets its phone columns
**Decision:** Below `md` (768 px) the 256 px sidebar becomes a top bar with a menu button, and a drawer built on Radix Dialog (`apps/web/src/components/mobile-nav.tsx:26,31,41`) holds the same navigation, user and Sign out. The shell is `flex h-dvh flex-col … md:flex-row` (`app/(dashboard)/layout.tsx:15`) and the sidebar is `hidden … md:flex` (`components/sidebar.tsx:66`). Project tabs scroll sideways (`project-nav.tsx:29`), the API Keys table is a table from `md` and one card per key below it (`api-keys-panel.tsx:124,150`), and dialogs are `calc(100vw - 2rem)` wide and scroll when taller than the screen (`components/ui/dialog.tsx:36`). The rule: **a grid that sets its columns only at a breakpoint must also set its phone columns (`grid-cols-1`), and a column that holds wide content needs `min-w-0`** (`tool-list.tsx:206`, `projects/page.tsx:36`). A test scans every component and page for the pattern (`apps/web/src/test/phone-layout.test.ts:212,216`), and checks that the scan finds grids at all.
**Why:** At 375 px the sidebar left about 119 px for the page. The Radix drawer was chosen over a hand-built one because focus trapping, Esc, closing on an outside tap and returning focus to the button come with it, and the package was already in use for the dialogs, so no new dependency. The grid rule came from a measured bug: the Edit tool dialog's Schema preview tab scrolled sideways (dialog 393 px of content in a 326 px box). Cause: `grid gap-4 sm:grid-cols-2` has no column template below `sm`, so it gets one implicit `auto` column, and a grid item's minimum width is its content, so the widest line of JSON stretched the column. Reproduced in headless Chrome at a true 375 px viewport with the real compiled CSS, switching one candidate at a time: the dialog's own single-column fix alone was not enough (369 vs 326); `grid-cols-1` plus `min-w-0` on the columns gave 326 vs 326. The same pattern was on the Projects page, where a 48-character slug would have widened the whole page. A unit test cannot measure layout, so the scan checks the classes and the measurement is what shows they are the right ones; real-browser flows are the Playwright work in 5b. What the tests do not cover is what an open drawer does (Esc, focus trap and return), which is Radix's and was checked by hand at 375 px.

### `next dev` binds 127.0.0.1
**Decision:** The web app's dev script is `next dev --hostname 127.0.0.1 --port 3000` (`apps/web/package.json:6`). `next start` is unchanged (`:8`), since production hosts and CI set their own address. A test pins both scripts.
**Why:** Next's default is `0.0.0.0` (`next dev --help`), which exposed the development dashboard to the local network. The gateway already binds `127.0.0.1` outside production (`apps/gateway/src/env-schema.ts:64`). `http://localhost:3000` keeps working on Windows even though `localhost` resolves to `::1` first, then `127.0.0.1` here: the client is refused on `::1` and falls back. Measured with a throwaway listener bound the same way: Node `fetch`, curl and headless Chrome all reached it through `localhost`, while `[::1]` and the machine's LAN address were refused. `AUTH_URL` and the GitHub callback still say `localhost:3000` (`.env.example:16,19`), cookies are host-only for `localhost`, and nothing in the gateway or worker calls the web app, so nothing else depends on the bind address. Opening the dashboard as `127.0.0.1` does not match `AUTH_URL`, as before; the README says to use `localhost`, and how to override the bind for a phone.

### GitHub Actions at their current majors
**Decision:** `actions/checkout` v4 → v7, `pnpm/action-setup` v4 → v6, `actions/setup-node` v4 → v7 (`.github/workflows/ci.yml:50,52,54,154`), as floating major tags, as before.
**Why:** The v4 actions run on the Node 20 runtime; checkout, setup-node and pnpm/action-setup moved to Node 24 from v5 on. The release notes were read for every major crossed (the list is in the commit message `b187d14`); none touches this workflow. `checkout` v6 stores credentials in a separate file and v7 refuses fork pull requests under `pull_request_target`, but no step runs `git` and the triggers are `push` and `pull_request`. `setup-node` v5 turned on automatic caching when `packageManager` is set and v6 limited it to npm, but the workflow sets `cache: pnpm` explicitly. `pnpm/action-setup` v6.1.0 is the first release that supports pnpm 12, the version in `packageManager` (`package.json:29`), and it still reads that field because no `version:` input is set. The check was CI itself: both required checks stayed green and the runs carried no Node 20 deprecation annotation. Not done: pinning to commit SHAs, which would protect against a moved tag at the price of manual bumps.

### Node 22.23.3 everywhere, floor 22.19
**Decision:** `engines.node` is `>=22.19.0` (`package.json:26`). CI (`.github/workflows/ci.yml`), the gateway Dockerfile (`ARG NODE_VERSION`) and `.nvmrc` pin the exact patch `22.23.3`, each with a comment to keep the three in step. The CI image job checks `node -v` inside the image. The Inspector v1 commands and screens, which existed only for Node below 22.19, are gone from the Connect tab and the README; Inspector stays at 2.11.0.
**Why:** Inspector 2.x declares `node >=22.19.0`, so that is the lowest version that runs everything we document. An exact patch keeps CI and the image reproducible: a Node point release cannot change a green run without a commit. The cost is a manual bump in three places, which the comments and the image check make visible.

### `DATABASE_CONNECT_TIMEOUT_MS`: a dead database fails fast
**Decision:** `packages/db` passes `connectionTimeoutMillis` to the pg pool (`packages/db/src/index.ts`), read from `DATABASE_CONNECT_TIMEOUT_MS`. Default 5 s for the dashboard and the gateway; the worker sets 10 s in `apps/worker/src/env.ts`. Idle and query timeouts are left alone.
**Why:** pg's default is no limit. Measured on Windows with the real client: a closed port failed in 0.2 s, a host that drops packets after 21.7 s, and a listener that accepts and never answers never failed (still waiting at 45 s), which is what hung the dashboard's error page in the Phase 5a check. With the limit the last two fail in about 3 s. 5 s leaves room for a suspended hosted database (Neon's free tier) to wake and for a human-facing page to answer; the worker's jobs are retried and nobody waits on them. The timeout also bounds the wait for a free pool slot, so a small pool cannot stay full of hung connection attempts (tested with `max: 2` and five queries). The tests use a closed port and a silent local listener, so they need no Docker.

**Known limitation: an open pooled connection to a silently dead database can hang beyond the connect timeout.** `connectionTimeoutMillis` covers opening a connection (and waiting for a free pool slot), not a query on a connection that is already open. Measured with a TCP relay in front of the dev database, frozen after two healthy queries (sockets left open, no bytes flowing) and a 1000 ms connect timeout: the next query was still waiting after 30,027 ms. What ends such a wait in practice is whatever finally closes the socket (a proxy, the OS, the server). Not fixed here. The options, to be decided in the deploy task once Neon's behaviour on suspend is known: `query_timeout` (a hard cap on any query, so it also cuts off slow analytics queries), TCP keepalive (does not help when a proxy keeps the socket open on our side), or a shorter idle timeout (pg-pool closes idle connections after 10 s by default, which already limits the window).

**Browser check (Windows, Docker Desktop, `next dev`), with Postgres stopped:** the server answered `/projects` in under 0.6 s (navigation timing `responseEnd` 573 ms) and the error page appeared after 10.0 s, so the remaining ~9 s was in the browser, not in the database layer. The pool had been idle for about 5 minutes, so no stale connection was involved. Fetches right after the stop took 2.0 s (`/projects`) and 5.1 s (`/projects/petstore-demo/overview`, consistent with the 5 s connect timeout). "Try again" with Postgres still down failed in 0.4 s, and after `docker compose start postgres` it recovered in 1.1 s with no restart. A server render makes one database call per page (`/projects`: one `findMany`; project pages: `getProject` in the layout and the page, in parallel), so a wait never doubles. The dev-mode browser delay is not investigated further; it is checked on a production build during deploy.
